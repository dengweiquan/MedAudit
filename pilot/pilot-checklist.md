# MedAudit 试点实施清单（对应 0.36.0-m36）

## 一、试点前置条件（逐项核对）

**服务端**

- [ ] 试点服务器就位（Linux amd64，2 核/4GB/10GB 起步），已按 deployment-guide 完成安装
- [ ] **本站医院已初始化**：服务端环境已设 `MEDAUDIT_SITE_HOSPITAL_ID` / `MEDAUDIT_SITE_HOSPITAL_NAME` 并重启，管理页显示「本站信息」、工作台进度只显本院
- [ ] **默认口令已修改**：admin 首次登录后已改口令（至少 8 位），新口令经安全渠道交接
- [ ] **两种界面模式已向院方说明**：默认医院模式（首页/审计对象/问题/报告/复检对比 5 菜单）；顶栏「工程师模式」开关打开后可见审计记录/基线/规则/关联分析/管理——只是界面显示切换，不是权限控制
- [ ] **超级令牌有效期与来源限制已确认**：如用令牌登录（`ma token` 铸造，原文只返回一次），令牌缺省有效期 90 天、最长 365 天（`ma token -d 天数`），过期须重新生成；来源限制 `MEDAUDIT_TOKEN_ALLOW_CIDR`（逗号分隔网段）设置后仅范围内来源可令牌登录，任一条非法即全部拒绝且启动时打印警告；口令登录不受来源限制影响
- [ ] `smoke-test.sh`（带 MEDAUDIT_USER/MEDAUDIT_PASS）全绿；工作台可从试点办公网打开（或已配反向代理）
- [ ] 证据加密决策已定：启用则 evidence.env 已生成并单独保管；不启用则留有书面说明
- [ ] 定期自动复检决策已定：启用则证据密钥（MEDAUDIT_EVIDENCE_KEY）已配置并单独保管，在管理页「定期自动复检」为首批资产开启周期；口令加密保存、不以明文出现
- [ ] 告警有人看：定期复检失败会写告警，明确由谁确认并跟进（失败不静默）
- [ ] 平台库备份方式已定（`ma srvbak` 在线快照或 sqlite `.backup`；切勿直拷运行中的库主文件），并演练过一次恢复打开

**目标与账号**

- [ ] 试点目标清单确认（建议首批：1 个核心数据库 + 1 台应用主机 + 其上中间件，跑通再扩）
- [ ] 每个数据库备好只读审计账号并验证可登录（口令经安全渠道交付操作人，不入任何文档）
- [ ] OS/中间件目标备好登录账号；Windows 目标确认 WinRM 已启用（5985）
- [ ] 网络连通性逐项实测：按 deployment-guide 第 3 节矩阵逐条验证
- [ ] Windows 推送的 server_url 已定（目标机可达的服务地址）并在目标机上实测可打开

**例外口径（先与院方对齐再审计）**

- [ ] 厂商必需账号清单已与院方确认（如 Oracle SYS/SYSTEM 须保留、厂商系统账号、内置超级用户）：决定逐项走**基线**（点名主体）还是**规则启停**（整项检查关闭，须填原因）
- [ ] 例外清单留痕：每条基线写明原因；每个关闭的规则在「规则」页填关闭原因
- [ ] 基线可从模板套用：HIS/LIS/PACS/通用厂商模板在管理页一键套用为基线，占位账号须填现场实际账号后才生效

**组织与窗口**

- [ ] 试点窗口与联系人确认（院方信息科对接人、运维值班）
- [ ] 明确告知口径：平台只读采集、不改目标配置；采集时段与业务高峰错峰
- [ ] 报告交付对象与问题整改责任人已定

## 二、试点执行步骤

1. 在「管理」页登记首批资产（本站医院自动锁定），远程参数一并登记。
2. 逐资产在「审计对象」页点「开始审计」/「远程审计」，确认执行结论：COMPLETE，或 PARTIAL 且原因明确（权限/上限）。
3. 如有已批例外：先建基线（可手工建或从模板套用，占位须填现场实际账号）、按需关规则，再评估（开始审计弹窗可选基线）。
4. 在「问题」页按规则分组过一轮：确认问题清单与院方认知一致，UNKNOWN 给出补采或边界说明。
5. 跑一次关联分析（同院多包），确认提权路径结论可向院方讲解。
6. 在「报告」页按对象生成报告并下载 Word：核对封面信息、执行摘要的问题分布、修复与回滚脚本章节；抽查 1 条脚本与问题明细一致。
7. 选取 1–2 个确认问题走完整闭环：负责人按报告脚本整改 → 再次审计 → 「复检对比」确认已修复。

## 三、试点验收标准

- [ ] 首批资产全部完成采集与评估，执行结论无 FAILED（或 FAILED 已定位为环境问题并记录）
- [ ] 至少一份正式 Word 报告（新版式：含问题分布与修复脚本章节）产出并经院方对接人确认可读
- [ ] 确认问题均有处置结论；至少一个问题完成「整改 → 再审计 → 复检对比确认」闭环
- [ ] 关联分析至少运行一次，路径结论（含「未发现路径」）可解释
- [ ] 基线与规则启停如有使用，原因留痕完整且与院方确认一致
- [ ] 模板套用的基线已核对：占位账号填的是现场实际账号，无占位符残留
- [ ] 如开启定期复检：至少一次自动执行完成（或失败告警已确认并定位原因）
- [ ] 全程无口令落库/落文档事件；平台库备份可恢复验证一次

## 四、演示动线（load-demo.sh 加载后，约 10 分钟）

> 演示数据请加载到未设本站、或本站医院即 h-demo 的实例（脚本登记演示医院 h-demo）。

1. **首页（工作台）**：类别问题卡与医院整改进度一屏可见——哪类有问题、各多少项、最近审计时间；演示医院的待整改数与进度状态。
2. **审计对象页**（切到数据库筛选）：PostgreSQL 的 hba 配置类问题；对 MySQL 对象点「问题」看按规则分组的清单。
3. **审计记录页**（工程师模式）：MySQL 第二包开「工程师详情」——「漂移对比」看两包之间多出的角色、授权与 local_infile 配置变化；「有效权限」看 demo_via 经角色链派生 SUPER（直接授权里看不到）。
4. **关联分析页**：两组路径——Oracle 角色嵌套（PDB_DBA_TEST → DBA）；Linux 组 tomcatops 写 Tomcat 配置 → 以 root 运行的跨层链（起点是普通用户 nurse1）。
5. **报告页**：按对象生成 MySQL/Oracle 报告，Word 里执行摘要、问题分布、提权路径、漂移、修复脚本章节齐全；业务接口对象同样在报告页下载 API 报告 Word（6 条越权命中）。
6. 收尾问答要点：只读采集、口令不落库、UNKNOWN 不等于安全、PARTIAL 的诚实口径（见操作手册第 9 节）。
